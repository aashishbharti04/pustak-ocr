पुस्तक Pustak-OCR

Turn a scanned Hindi book into clean text. OCR does the first pass, Claude reads the scan and points at what looks wrong, and you stay the one who decides.

View on GitHub Why it suggests instead of rewrites

Devanagari OCR is good enough to save you most of the typing and bad enough that you still have to read every page. Pustak-OCR is built around that fact rather than pretending otherwise.

Upload a scanned PDF. Each page is rendered at 300 DPI, deskewed, and run through Tesseract. You then work through the book in a split-screen review UI — the scan on the left, an editable text box on the right — and export to DOCX, EPUB, or plain text when you're done. Everything runs on your own machine; no page images or text leave it.

The pipeline

Why it suggests instead of rewrites

The obvious thing to build is: OCR the page, hand the text to an LLM, ask it to fix the mistakes, keep the output. That version is worse than useless, and it's worth being precise about why.

An LLM told "fix the OCR errors, don't rewrite" will do exactly that about 95% of the time. The problem is the other 5%. On a word it genuinely cannot recover, it doesn't fail loudly — it emits a different plausible Hindi word that fits the sentence.

That asymmetry is the whole problem. A raw OCR error looks like garbage (रामप्रसाट) and your eye snags on it. An LLM's error looks like prose, and your eye slides straight over it. Over 282 pages you will not catch them, and you'll have no way to know which pages were touched. An unsupervised LLM pass converts visible errors into invisible ones.

So the model never produces the document. Two mechanisms enforce that:

1. It sees the page

The scan goes with the text on every request. A model that can't see the page can only guess fluently at a damaged matra; one that can is actually reading it. Every suggestion has to be justified by what is visibly printed — not by what reads well.

2. Every span must be anchored

Each suggestion names an original span that must occur verbatim in the OCR text. If it doesn't, the suggestion is discarded server-side before you ever see it. A span the model invented cannot be located, so it cannot be applied — fabrication fails closed.

रामप्रसाट→रामप्रसाद kept final consonant is द, not ट
मंदिर की घंटी→मन्दिर की घंटी discarded span isn't in the OCR text — the model invented it

The panel reports how many it dropped. A count that's consistently above zero is a signal to distrust that page's suggestions — not to ignore the counter.

The point isn't correction, it's attention

Reviewing eight flagged words takes about thirty seconds. Reading a whole page takes about four minutes. Across a book that's the difference between an evening and a fortnight — and it never requires trusting the model with your text, only with pointing.

A note on preprocessing

Most OCR tutorials tell you to binarize and sharpen. Here binarization is off by default, deliberately. Tesseract binarizes internally (Otsu), and handing it a pre-binarized page usually makes Devanagari worse — adaptive thresholding eats the shirorekha and thins the matras, which is exactly the detail you can't afford to lose. Sharpening amplifies JPEG ringing into artifacts shaped like matras. The default is grayscale → denoise → deskew; binarization is a checkbox for genuinely bad scans.

Deskew uses a projection profile rather than Hough lines, which suits the script: the shirorekha makes every text line a strong horizontal bar, so row variance peaks sharply at the true angle. On synthetic pages it recovers ±6° to within 0.01°.

Setup

git clone https://github.com/aashishbharti04/pustak-ocr
cd pustak-ocr
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn pustak_ocr.app:app --port 8077

Tesseract is a separate binary — install it with the Hindi (hin) language data, or OCR won't start. The Claude panel needs ANTHROPIC_API_KEY; without it everything else still works. The home page tells you exactly what's missing.

Honest limitations

Two paths are unverified

Neither Tesseract nor Claude credentials were available on the machine this was built on, so the Tesseract hin recognition call and the live Claude request have never been run for real. Everything around them is tested — render, preprocess, database, review UI, exports, the anchoring guard, the error paths. But the two steps that do the actual recognition are unproven. Your first real run is the first real test.

  • Single-column prose only. No tables, figures, or footnotes — a novel, not a textbook.
  • One OCR engine. No second engine to cross-check. Engine disagreement would be a strong, free attention signal; it isn't built.
  • Single-core OCR. One worker thread per book. Fine unattended; a pool would be much faster.
  • No authentication. Bind to localhost. This is a local tool and should stay one.
  • Cost. Roughly $0.03–0.08 per page for the Claude pass — an estimate, not a measurement. Run ten pages and check your bill.

Rights

The tool doesn't care what you feed it; you should. Digitizing a full book is reproduction whether OCR or a keyboard does the typing. Use it on your own manuscripts, public-domain texts, or works you have permission to copy.
